1. BASIC SELECT + FILTERING

Before SQL, let's use a real-life example.

Imagine (Toy Box):

A toy box filled with toys:

toy_namecolortype
Teddy BearBrownPlush
Toy CarRedVehicle
Lego BlockRedBlocks
Business asks:

Which toys are RED?

SELECT + WHERE

Think: "Look inside the toy box (FROM toys), check each toy to see if it is Red (WHERE color = 'Red'), and write down their names (SELECT toy_name)."

SQL 
SELECT toy_name
FROM toys
WHERE color = 'Red';
How SQL Thinks:
  • For Teddy Bear: Color is Brown. Is it Red? NO → Discard.
  • For Toy Car: Color is Red. Is it Red? YES → Keep.
  • For Lego Block: Color is Red. Is it Red? YES → Keep.
Output:
toy_name
Toy Car
Lego Block
💡 Important Connection:

The WHERE clause acts like a physical filter screen. It stops unwanted rows immediately so they don't consume memory in the next steps (like sorting or displaying).

🔑 Easy Memory Trick:
  • SELECT: Your Eyes 👀 (what columns to look at).
  • FROM: The Toy Chest 🗄️ (which table contains the records).
  • WHERE: The Gatekeeper 👮 (who gets inside).
🚀 Why Data Engineers Care:

In big data pipelines (e.g. Spark / Databricks), filtering early (called "Filter Pushdown") saves millions of gigabytes of network transfer by discarding unused records before they are shuffled across cloud servers.

2. GROUP BY + HAVING

Before SQL, let's use a real-life example.

Imagine (Candies):

A bag of mixed candies:

candy_namestatus
SnickersFresh
KitKatFresh
SnickersFresh
SkittlesExpired
KitKatFresh
Business asks:

Which fresh candies do we have 2 or more of?

GROUP BY vs HAVING

Think: "First, throw away expired candies (WHERE). Second, group identical candies into piles (GROUP BY). Third, count each pile and only keep piles with 2 or more candies (HAVING)."

SQL 
SELECT candy_name, COUNT(*) as qty
FROM candies
WHERE status = 'Fresh'
GROUP BY candy_name
HAVING COUNT(*) >= 2;
How SQL Thinks:
  • Filter (WHERE): Drop Skittles because it is expired. Remaining candies: Snickers, KitKat, Snickers, KitKat.
  • Group (GROUP BY): Put them in piles:
    • Pile Snickers: 2 pieces.
    • Pile KitKat: 2 pieces.
  • Filter Groups (HAVING): Check pile sizes:
    • Snickers pile has 2 pieces (>= 2)? YES → Keep.
    • KitKat pile has 2 pieces (>= 2)? YES → Keep.
Output:
candy_nameqty
Snickers2
KitKat2
💡 Important Connection:

You cannot use WHERE to check the size of a group (like WHERE COUNT(*) >= 2) because the database doesn't know the group size until after the grouping is completed. That's why we use HAVING.

🔑 Easy Memory Trick:
  • WHERE: Filters individual candies before they are put into bowls.
  • GROUP BY: Groups them into bowls.
  • HAVING: Filters the bowls after checking their weights on a scale.
🚀 Why Data Engineers Care:

Putting row-level filters in HAVING (e.g. HAVING status = 'Fresh') is a performance disaster. It forces the database to group records it should have discarded immediately in WHERE. Keep row filters in WHERE, aggregate filters in HAVING!

3. DUPLICATE DETECTION

Before SQL, let's use a real-life example.

Imagine (Logs):

An API log capturing customer logins, where API retries caused duplicate logs:

log_idcustomer_idlogin_time
110110:00:00
210110:00:00
310210:01:00
410310:02:00
Business asks:

Which login records are duplicate (same customer and login time)?

Deduplication Pattern

Think: "Group by customer_id and login_time. Count the matching records. If the count is greater than 1, we found our duplicates!"

SQL 
SELECT customer_id, login_time, COUNT(*) as occur
FROM login_logs
GROUP BY customer_id, login_time
HAVING COUNT(*) > 1;
How SQL Thinks:
  • Group columns: customer_id and login_time:
    • Pile (101, 10:00:00): Contains log 1 & 2. Count = 2.
    • Pile (102, 10:01:00): Contains log 3. Count = 1.
    • Pile (103, 10:02:00): Contains log 4. Count = 1.
  • Filter groups having occur > 1:
    • Pile (101, 10:00:00) has count 2 (> 1)? YES → Keep.
    • Pile (102, 10:01:00) has count 1 (> 1)? NO → Discard.
Output:
customer_idlogin_timeoccur
10110:00:002
💡 Important Connection:

Duplicates are the main cause of reconciliation failures in ETL. They corrupt sales totals and inflate analytics. Tracking count occurrences per business key is the fundamental rule of data quality pipelines.

🔑 Easy Memory Trick:

GROUP BY key columns + HAVING COUNT(*) > 1 is your Clone Alarm. Whenever the alarm count is > 1, you have identical clones in your system!

🚀 Why Data Engineers Care:

In standard data integration pipelines, duplicate detection is run inside staging layers to dump corrupted load records into a "Dead Letter Queue" (DLQ) so developers can debug API errors without stopping the ingestion pipeline.

4. NULL VALIDATION

Before SQL, let's use a real-life example.

Imagine (Phones):

A classroom list containing student names and their phone numbers. Some kids don't have a phone:

student_namephone_number
Alice123-456
BobNULL
CharlieNULL
Business asks:

Which students are missing their phone numbers?

The Ghost Operator (IS NULL)

Think: "In databases, NULL represents a Ghost (missing/unknown). You can't ask phone = NULL because you cannot compare a phone to a ghost. You must ask phone IS NULL."

SQL 
SELECT student_name
FROM students
WHERE phone_number IS NULL;
How SQL Thinks:
  • For Alice: phone_number is '123-456'. Is it a ghost? NO → Discard.
  • For Bob: phone_number is NULL. Is it a ghost? YES → Keep.
  • For Charlie: phone_number is NULL. Is it a ghost? YES → Keep.
Output:
student_name
Bob
Charlie
💡 Important Connection:

If you write WHERE phone = NULL, SQL returns nothing (0 rows). This is because the database evaluates AnyValue = NULL as UNKNOWN, which evaluates to False. Always use IS NULL or IS NOT NULL.

🔑 Easy Memory Trick:

NULL is a Ghost. You cannot compare a real object to a ghost using equals (=). You must ask: "Is it haunted?" (IS NULL).

🚀 Why Data Engineers Care:

During ETL migrations, missing records or failed joins display as NULL. Counting NULL columns is the most common check in Data Quality frameworks (like Great Expectations) to detect broken upstream schemas.

6. ROW_NUMBER()

Before SQL, let's use a real-life example.

Imagine (Purchases):

A grocery store checkout line where customers get ticket numbers grouped by their customer group:

customer_idpurchase_timeamount
10109:00:00$50
10110:00:00$120
10209:30:00$40
Business asks:

For each customer, number their purchases sequentially from first to last.

Windowing - ROW_NUMBER()

Think: "Divide the table into groups for each customer (PARTITION BY customer_id). Inside each group, arrange purchases chronologically (ORDER BY purchase_time ASC). Assign ticket numbers (ROW_NUMBER())."

SQL 
SELECT customer_id, purchase_time, amount,
       ROW_NUMBER() OVER (
           PARTITION BY customer_id
           ORDER BY purchase_time ASC
       ) as purchase_seq
FROM purchases;
How SQL Thinks:
  • Partition (Split): Group records by customer_id:
    • Group 101: Contains purchases at 09:00:00 and 10:00:00.
    • Group 102: Contains purchase at 09:30:00.
  • Order & Number: Number sequentially inside each group:
    • Group 101:
      • 09:00:00 purchase gets row number 1.
      • 10:00:00 purchase gets row number 2.
    • Group 102:
      • 09:30:00 purchase gets row number 1.
Output:
customer_idpurchase_timeamountpurchase_seq
10109:00:00$501
10110:00:00$1202
10209:30:00$401
💡 Important Connection:

Unlike GROUP BY, which squashes the rows together into a single summary row, window functions keep all rows alive. They just add a calculated ticket number to each row.

🔑 Easy Memory Trick:

ROW_NUMBER = Bouncer with a Ticket Roll. The bouncer divides people into separate lines (PARTITION BY), sorts them (ORDER BY), and hands out tickets (1, 2, 3...). No two rows share a ticket.

🚀 Why Data Engineers Care:

ROW_NUMBER() is the primary tool for deduplication in Incremental loads. If API calls resend records, we number duplicates by load time desc and filter for rn = 1 to only write the latest record.

7. RANK() vs DENSE_RANK()

Before SQL, let's use a real-life example.

Imagine (Race):

A school race where two kids cross the finish line at the exact same second:

runner_namerace_time
Alice10 seconds
Bob12 seconds
Charlie12 seconds
David13 seconds
Business asks:

Assign rank positions to the runners. Show the differences between gap (RANK) and gapless (DENSE_RANK) positions.

Podium Gaps

Think: "If runners tie, how do we rank the runner behind them? In RANK(), we skip numbers (e.g. 1st, 2nd, 2nd, 4th). In DENSE_RANK(), we keep them tight with no gaps (e.g. 1st, 2nd, 2nd, 3rd)."

SQL 
SELECT runner_name, race_time,
       RANK() OVER (ORDER BY race_time ASC) as rk,
       DENSE_RANK() OVER (ORDER BY race_time ASC) as drk
FROM race;
How SQL Thinks:
  • Alice (10s): The fastest. Gets RANK 1 and DENSE_RANK 1.
  • Bob (12s) and Charlie (12s): A tie! Both get RANK 2 and DENSE_RANK 2.
  • David (13s): The next runner:
    • RANK() counts total runners ahead (3). So David gets RANK 4. 3rd place is skipped!
    • DENSE_RANK() counts unique ranks ahead (2). So David gets RANK 3. No podium numbers are skipped!
Output:
runner_namerace_timerkdrk
Alice10s11
Bob12s22
Charlie12s22
David13s43
💡 Important Connection:

Never use RANK() for deduplicating data logs! If duplicates have identical timestamps, they both receive rank 1. Filtering for WHERE rk = 1 will load BOTH duplicates, causing verification failures.

🔑 Easy Memory Trick:
  • RANK: Skips rankings on ties (Olympics: 1st, 2nd, 2nd, 4th).
  • DENSE_RANK: Densely packed ranks (No gaps: 1st, 2nd, 2nd, 3rd).
🚀 Why Data Engineers Care:

Top-N queries (e.g. "Find the top 3 highest revenue regions") require DENSE_RANK so that if multiple regions tie for second place, we don't skip the next region entirely from our report.

8. LATEST RECORD VALIDATION

Before SQL, let's use a real-life example.

Imagine (Profiles):

A profile audit log where users change their email addresses multiple times over the week:

user_idemailupdate_time
1a@old.com10:00:00
1a@new.com15:00:00
2b@old.com09:00:00
Business asks:

What is the CURRENT active email address for each user?

CDC Log Rewinding (rn = 1)

Think: "For each user, sort updates from newest to oldest (ORDER BY update_time DESC) inside their group (PARTITION BY user_id). The row numbered 1 is their latest email."

SQL 
SELECT user_id, email, update_time
FROM (
    SELECT user_id, email, update_time,
           ROW_NUMBER() OVER (
               PARTITION BY user_id
               ORDER BY update_time DESC
           ) as rn
    FROM profile_updates
)
WHERE rn = 1;
How SQL Thinks:
  • Subquery Partitions: Group updates per user:
    • User 1:
      • a@new.com (15:00) gets rn = 1.
      • a@old.com (10:00) gets rn = 2.
    • User 2:
      • b@old.com (09:00) gets rn = 1.
  • Outer Query Filter: Filters for rn = 1:
    • Keep User 1 (a@new.com) and User 2 (b@old.com).
Output:
user_idemailupdate_time
1a@new.com15:00:00
2b@old.com09:00:00
💡 Important Connection:

Without an ordering sequence column (like a timestamp, version count, or incremental primary key), extracting the latest state is mathematically impossible. Always design audit logs with sequence markers!

🔑 Easy Memory Trick:

The CDC Rewind: Partition by ID + Order by Time DESC + Filter rn = 1 is your magical timeline rewinder. It rewinds history and returns only the final frame.

🚀 Why Data Engineers Care:

This pattern is the core of Change Data Capture (CDC) logic. Systems like Debezium emit logs for every single insert/update. Before loading them to target tables (SCD Type 1), we apply this filter to write only the final state.

9. INNER JOIN

Before SQL, let's use a real-life example.

Imagine (Left Socks basket):

Left socks and Right socks inside separate baskets:

left_idcolor
1Blue
2Red
3Green

Right Socks basket:

right_idcolor
101Blue
102Red
103Yellow
Business asks:

Match left and right socks to make pairs. What happens to unmatched socks?

The Sock Matcher (INNER JOIN)

Think: "Only keep socks that find a matching color in both baskets. If a sock cannot be paired, discard it completely."

SQL 
SELECT l.color as left_sock, r.color as right_sock
FROM left_socks l
INNER JOIN right_socks r
ON l.color = r.color;
How SQL Thinks:
  • Left Blue matches Right Blue? YES → Keep pair (Blue, Blue).
  • Left Red matches Right Red? YES → Keep pair (Red, Red).
  • Left Green matches Right Green? NO → Throw left Green away.
  • Right Yellow matches Left Yellow? NO → Throw right Yellow away.
Output:
left_sockright_sock
BlueBlue
RedRed
💡 Important Connection:

An INNER JOIN matches like mathematical intersection ($A \cap B$). If there are duplicates of a key in both baskets (e.g. 2 blue lefts and 2 blue rights), you get $2 \times 2 = 4$ pairs! This multiplication is called a Join Explosion.

🔑 Easy Memory Trick:

Couples Only Club: INNER JOIN deletes unmatched items on both sides. If you don't have a matching partner on the key columns, you cannot enter the output table.

🚀 Why Data Engineers Care:

If your upstream dimension keys have typos or blank rows, an INNER JOIN will silently drop transaction records from your output tables! Always audit row count before and after joins to detect data loss.

10. LEFT JOIN

Before SQL, let's use a real-life example.

Imagine (Birthday Party):

A birthday party guest list (Left table) and gift bags (Right table):

guest_name
Sam
Lea
Tom

Gift Bags:

namegift
SamToy Car
LeaBook
Business asks:

Show every guest on the invitation list and what gift they received.

The Guest Shield (LEFT JOIN)

Think: "Protect the guest list (Left table) at all costs. If a guest has no matching gift bag, let them stay, but their gift column is empty (NULL)."

SQL 
SELECT g.guest_name, b.gift
FROM guests g
LEFT JOIN gift_bags b
ON g.guest_name = b.name;
How SQL Thinks:
  • Sam (Guest) matches Sam (Gift: Toy Car) → Output (Sam, Toy Car).
  • Lea (Guest) matches Lea (Gift: Book) → Output (Lea, Book).
  • Tom (Guest) has no matching gift bag → Protect Tom, set gift to **NULL**. Output (Tom, NULL).
Output:
guest_namegift
SamToy Car
LeaBook
TomNULL
💡 Important Connection:

Standard pattern in data warehousing: fact_sales LEFT JOIN dim_products. This guarantees that even if a product ID doesn't exist in our lookup table, the financial transaction is never dropped (it just shows NULL columns).

🔑 Easy Memory Trick:

The Safe Party: Left table is the guest list. Guests are protected. If they don't have matching details on the right, they get a ghost (NULL) instead of being kicked out.

🚀 Why Data Engineers Care:

LEFT JOIN is the default tool for enriching transaction data. It prevents data loss and highlights missing dimensions as NULLs, allowing engineers to debug source data issues easily.

11. MISSING RECORD VALIDATION

Before SQL, let's use a real-life example.

Imagine (Source vs Target):

A source list of files uploaded (Left table) vs files currently written to storage (Right table):

file_id
101
102
103

Storage files target:

file_id
101
102
Business asks:

Identify files that failed to copy over to storage during migration.

The Orphan Finder (LEFT JOIN + IS NULL)

Think: "Left join Source to Storage. If a file exists in Source but has no match in Storage, its Storage key will be NULL. Filter for those NULL keys!"

SQL 
SELECT s.file_id
FROM source s
LEFT JOIN storage t
ON s.file_id = t.file_id
WHERE t.file_id IS NULL;
How SQL Thinks:
  • Source file 101 matches Storage file 101 → t.file_id = 101.
  • Source file 102 matches Storage file 102 → t.file_id = 102.
  • Source file 103 has no Storage match → t.file_id = NULL.
  • Filter (WHERE t.file_id IS NULL): Keep file 103 because its target key is NULL.
Output:
file_id
103
💡 Important Connection:

This performs the same business logic as a NOT EXISTS filter. However, LEFT JOIN evaluates and builds all matching rows in memory first, which can slow down queries compared to EXISTS.

🔑 Easy Memory Trick:

LEFT JOIN + NULL Filter = The Orphan Finder. We list all children, look up their parents, and keep only children whose parent column is a blank ghost (NULL).

🚀 Why Data Engineers Care:

Missing record validation is the primary reconciliation check run after database migrations or CDC loads to ensure 100% data replication integrity.

4. EXISTS vs NOT EXISTS

Before SQL, let's use a real-life example.

Imagine (Customers & Orders):

Customers table:

customer_id
101
102
103

Orders table:

customer_id
101
101
102
Business asks:

Which customers have placed at least one order?

EXISTS

Think: "Does at least one matching record exist? If YES → keep row."

SQL 
SELECT *
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE c.customer_id = o.customer_id
);
How SQL Thinks:
  • For customer 101: Does order exist? YES → Keep 101.
  • For customer 102: Does order exist? YES → Keep 102.
  • For customer 103: Does order exist? NO → Discard 103.
Output:
customer_id
101
102
NOT EXISTS

Think: "No matching record should exist. Keep rows that have no match."

SQL 
SELECT *
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE c.customer_id = o.customer_id
);
SQL Thinking:
  • For 101: Order exists → Reject.
  • For 102: Order exists → Reject.
  • For 103: No order exists → Keep 103.
Output:
customer_id
103
💡 Important Connection:

You already know this pattern:

SELECT c.customer_id
FROM customers c
LEFT JOIN orders o
ON c.customer_id = o.customer_id
WHERE o.customer_id IS NULL;

This also returns customer_id 103. Both solve the same business problem but use different SQL styles.

🔑 Easy Memory Trick:
  • LEFT JOIN + NULL: Find records missing in target (Dumps and filters).
  • NOT EXISTS: Find records that have no match (Alert scanner).
🚀 Why Data Engineers Use EXISTS:

Suppose customer 101 has 1,000,000 orders. EXISTS stops checking after finding the first matching order. It doesn't care if there are 999,999 more! That is why EXISTS is incredibly fast and commonly used for incremental loads, reconciliation checks, duplicate prevention, and validation rules.

9. COALESCE

Before SQL, let's use a real-life example.

Imagine (Contacts):

A contact list where kids list their Home Phone, Mobile, or Parent's Phone. Some numbers are missing (NULL):

student_namehome_phonemobileparent_phone
Alice555-001NULL555-999
BobNULL555-002NULL
CharlieNULLNULLNULL
Business asks:

Extract the primary contact method for each student. If no phone exists, default to 'No Phone'.

The Fallback Chain (COALESCE)

Think: "Scan columns from left to right and return the first value that is NOT a ghost (NULL). If they are all ghosts, return the fallback text."

SQL 
SELECT student_name,
       COALESCE(home_phone, mobile, parent_phone, 'No Phone') as primary_phone
FROM student_contacts;
How SQL Thinks:
  • For Alice: Check home_phone: '555-001' (Real!) → Stop scanning. Return '555-001'.
  • For Bob: Check home_phone: NULL (Ghost) → Scan next. Check mobile: '555-002' (Real!) → Stop scanning. Return '555-002'.
  • For Charlie: Check home_phone: NULL (Ghost) → Scan next. Check mobile: NULL (Ghost) → Scan next. Check parent_phone: NULL (Ghost) → Scan next. Check final text: 'No Phone' (Real!) → Return 'No Phone'.
Output:
student_nameprimary_phone
Alice555-001
Bob555-002
CharlieNo Phone
💡 Important Connection:

Remember that doing math with NULL makes the whole result NULL! E.g. salary + bonus is NULL if bonus is NULL. Use COALESCE(salary, 0) + COALESCE(bonus, 0) to safely add them.

🔑 Easy Memory Trick:

The Backup Team: COALESCE is your phone tree. You try to call home, then mobile, then parent. First one that answers gets picked!

🚀 Why Data Engineers Care:

Essential when cleaning raw ingest data in Silver lakehouse layers. We replace NULL values in keys, regions, or amounts with standard defaults (e.g. -1, 'Unknown', 0.0) to ensure analytics queries don't break.

10. MERGE / UPSERT THINKING (Conceptual)

Before SQL, let's use a real-life example.

Imagine (The Stencil & Drawing):

You have a drawing board (Target) and a new set of shapes (Source):

shape_idcolor
CircleRed (already drawn)
SquareBlue (already drawn)

New incoming sheet (Source):

shape_idcolor
CircleYellow (update color!)
TriangleGreen (new shape!)
Business asks:

Synchronize the drawing board with the new sheet. How do we apply the changes?

MERGE / UPSERT

Think: "If a shape already exists on our board, paint over it with the new color (UPDATE). If it doesn't exist, draw it from scratch (INSERT). That is UPdate + inSERT = UPSERT."

CONCEPTUAL SQL (MERGE) 
MERGE INTO target_table t
USING source_table s
ON t.id = s.id
WHEN MATCHED THEN
    UPDATE SET t.color = s.color
WHEN NOT MATCHED THEN
    INSERT (id, color) VALUES (s.id, s.color);
How SQL Thinks:
  • Check Circle: Exists in Target? YES (Matched) → Update color from Red to Yellow.
  • Check Square: Exists in Source? NO (No incoming changes) → Keep as is (Blue).
  • Check Triangle: Exists in Target? NO (Not matched) → Insert new shape (Triangle, Green).
Output Target Table:
shape_idcolor
CircleYellow
SquareBlue
TriangleGreen
💡 Important Connection:

In standard data warehouses like Delta Lake (Databricks) or Snowflake, running a raw INSERT every day causes duplicate records. A MERGE statement ensures we maintain a single, clean version of truth by comparing key columns.

🔑 Easy Memory Trick:

The Smart Clipboard: Think of a contact list on your phone. If you add a friend who is already there, you edit their profile (UPDATE). If they are new, you create a new contact card (INSERT). That's UPSERT!

🚀 Why Data Engineers Care:

Merge operations are the backbone of incremental load pipelines. Instead of reading and rewriting billions of rows every hour, we only process the tiny stream of updates and merge them in, saving massive cloud compute bills.

11. SCD (Slowly Changing Dimensions) Basics

Slowly Changing Dimensions (SCD) define how we handle changes to master lists (like a customer's city or an employee's department) over time.

Imagine (Customer moves city):

Customer 101 moves from Mumbai to Pune.

Before: 101 | Mumbai

After source update: 101 | Pune

SCD Type 1: Overwrite (No History)

Think: "Erase the old value and write the new one in its place. The history is gone forever."

Target becomes: 101 | Pune (Mumbai is lost!)

SCD Type 2: Add New Row (Full History Tracking)

Think: "Keep the old row, mark it as historical, and insert a brand new row with the current value and validity dates."

cust_idcityvalid_fromvalid_tois_current
101Mumbai2026-01-012026-05-31N
101Pune2026-06-019999-12-31Y
Comparing SCD 1 vs SCD 2:
  • SCD Type 1: Very simple. Uses less storage. Good when we don't care about the past (e.g. fixing a typo in a name).
  • SCD Type 2: Keeps history. Essential for business reports. If Alice bought products in January (when she lived in Mumbai) and in June (living in Pune), we can attribute sales to the correct city at the time of purchase.
💡 Important Connection:

SCD Type 2 uses date ranges (valid_from and valid_to) so that we can run point-in-time lookups (e.g., WHERE '2026-03-15' BETWEEN valid_from AND valid_to) to see what the state of data was at any exact second in the past.

🔑 Easy Memory Trick:
  • SCD Type 1 (The Whiteboard): Erase the old name, write the new name. No trace of the past.
  • SCD Type 2 (The Photo Album): Don't throw away your old baby photos when you grow up. Keep them and add a new photo with the new date!
🚀 Why Data Engineers Care:

Data warehousing relies on historical analysis. If you run SCD Type 1 on a customer's location, all past order reports will show their current city, distorting historical regional sales analytics. Type 2 is a MUST for accurate business intelligence.

12. DELETE DETECTION LOGIC

Before SQL, let's use a real-life example.

Imagine (The Missing Roll Call):

Yesterday, the source list had 3 kids. Today, it has 2. Kid 103 disappeared:

Yesterday Source: 101, 102, 103

Today Source: 101, 102

Our Target DB (currently has): 101, 102, 103

Business asks:

Identify which records were deleted from the source so we can update our target database.

Delete Detection Pattern

Think: "If a record exists in our Target but is missing in the incoming Source, it has been deleted. We perform a Target LEFT JOIN Source and keep rows where Source columns are NULL."

SQL 
SELECT t.customer_id
FROM target_table t
LEFT JOIN source_table s
ON t.customer_id = s.customer_id
WHERE s.customer_id IS NULL;
How SQL Thinks:
  • Match Target 101 with Source 101 → Found! (Keep in source list)
  • Match Target 102 with Source 102 → Found! (Keep in source list)
  • Match Target 103 with Source 103 → NULL! (Missing from source)
  • Filter (WHERE s.customer_id IS NULL): Keep 103. This is our deleted record!
💡 Important Connection:

In production, databases rarely use physical DELETE FROM queries because they erase history. Instead, they run an UPDATE to set a column like active_flag = 'N' or is_deleted = 1. This is called a Soft Delete.

🔑 Easy Memory Trick:
  • New Records (Insert): Source LEFT JOIN Target WHERE Target IS NULL (Source has it, Target doesn't).
  • Deleted Records (Delete): Target LEFT JOIN Source WHERE Source IS NULL (Target has it, Source doesn't).
🚀 Why Data Engineers Care:

A data engineer reports *what the data shows*, not what they assume happened. If a record is missing from the source, we say: 'Record exists in target but is missing from source.' This could mean a delete happened, or it could mean the source extract job failed and missed a record. We report, then investigate!

13. AUDIT COLUMNS

Audit columns are system metadata columns added to every database table to track when records were created and updated. They do not store business values; they store trace history.

Imagine (Record Birth & Changes):

A new customer record is born on June 1st:

customer_idcitycreated_dateupdated_date
101Pune2026-06-01NULL (or same as created)

The customer updates their city to Chennai on June 2nd:

customer_idcitycreated_dateupdated_date
101Chennai2026-06-012026-06-02
Audit Columns Rules
  • created_date: Set on the initial insert and **NEVER** changes. It represents the birth date of the record.
  • updated_date: Set to the current timestamp on every modification. It shows the last time the record was edited.
Real Interview Question:

"If a customer was created on Jan 1 and updated on Mar 1, what should happen to created_date after the update?"

Answer: Nothing! created_date remains Jan 1. Only updated_date changes to Mar 1.

💡 Important Connection:

Audit columns like updated_date are critical for **Incremental Loading**. Instead of reading all 100 million rows, the ETL pipeline queries: WHERE updated_date >= yesterday to only load the changed rows.

🔑 Easy Memory Trick:
  • created_date = Birth Certificate: Issued once when you are born. Never changes.
  • updated_date = Passport Stamps: Stamped every time you travel. Changes with every action.
🚀 Why Data Engineers Care:

Without audit columns, debugging pipeline failures is a nightmare. Audit columns tell us exactly when a row was modified, which ETL batch created it, and what pipeline run updated it, making data lineage and troubleshooting simple.
